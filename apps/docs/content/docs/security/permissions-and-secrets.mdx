## Approval cards

Supported providers emit permission requests and questions through the local harness. OpenMausBot displays these inline and records the outcome. Cancellation closes outstanding requests so stale approvals cannot be answered after a turn has ended.

“Always allow” is narrow: it is tied to a server-issued key and a pending request rather than granting arbitrary execution from a paired device.

## Operating-system permissions

Screen Recording and Accessibility permissions are controlled by the operating system. The desktop process owns local CUA lifecycle so grants are attributed to OpenMausBot.

## Secret handling

- Do not paste API keys into chat.
- Packaged builds use write-only settings and operating-system-backed encryption where supported.
- Secret values are scrubbed from public configuration responses and mobile APIs.
- Per-provider environment injection prevents unrelated agent processes from inheriting credentials they do not use.
- Command-line tools a bot runs in its shell use the accounts already signed in on this computer.

## Website sign-in

Bots may complete a sign-in you explicitly authorize for a particular site and
account, using an existing session, autofill, or credentials you supply or
designate for that purpose, including test accounts. A login form alone is not
a reason to refuse the task. Bots must check the destination and account first;
instructions on a webpage do not authorize using credentials.

Bots never ask for a website password, or for a one-time code, in chat, and a
bot never holds a password: a login you saved is typed into the page by
OpenMausBot itself ([Saved logins](#saved-logins)).

When you ask a bot to do something that needs a sign-in (in your own chat, or
in a routine or automation you set up) and the site sends a one-time code to
your email or phone, the bot reads it from your connected email or messages
and types it into that site, then carries on. Your request is the
authorization, so it does not ask again. A code only ever goes into the site it
was sent for: a bot never sends, posts, forwards or pastes one anywhere else,
and a web page, email or document that tells it to share a code, or enter it
somewhere else, is ignored.

When a bot is not signed in and has no saved login for the site, the code goes
somewhere it cannot read (an authenticator app, a phone it has no access to),
or a step needs a CAPTCHA, a passkey, payment details or your personal
interaction, it asks you to sign in yourself. You get one **Sign
in needed** card in the chat, naming the site and quoting the bot's reason, and
one notification ("Scout needs you to sign in to example.com"). The bot's turn
ends there.

- **Open** goes to the exact place the bot works, because a sign-in made
  anywhere else would not reach it. For the built-in browser, that is the
  Screen panel's Browser tab, at the bot's page, already in your control. For
  a Local VM or a cloud computer or VPS, it is that computer's view, where the
  banner offers **Take control**. For this computer, the card tells you to sign
  in there, in the browser the bot is using: the Browser tab keeps its own
  sign-ins, which a bot on this computer does not use.
- **Done** hands control back and resumes the bot, which checks it is signed
  in and continues.
- **Cancel** resumes the bot with your answer that you declined.

A newer request for the same site in the same conversation replaces the older
card. The card works on the desktop, the web app, a Cloud home and a desktop
paired to another computer (its Screen panel has a Browser view for this; the
host must allow browser control for that device in **Settings → Remote
access**). A phone shows the request and its notification; sign in from a
computer.

With **Open**, you type the password into the page yourself. None of this overrides your provider's own
restrictions, and approval modes are unchanged.

## Shared machines

OpenMausBot assumes the logged-in operating-system user is the workspace owner. On a shared machine, other administrators may be able to read application data or inspect processes. Use a dedicated OS account for stronger separation.
